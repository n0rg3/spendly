# @spendly/serverless — API чеков на Vercel

Автономная бессерверная функция: сама ходит на `suf.purs.gov.rs` и передаёт сырой текст
чека в Gemini 2.5 Flash. Весь разбор позиций, итог, дата и автокатегоризация выполняются
ОДНИМ вызовом LLM со `responseSchema` (Structured Outputs / JSON Mode) — на сервере нет ни
регулярных выражений для позиций, ни словарей-фолбэков, ни кэша «товар -> категория».
Локальный компьютер и ngrok не нужны — GitHub Pages обращается к публичному HTTPS-адресу Vercel.

## Как это работает

1. Функция скачивает страницу чека по `qrUrl` (валидация: только `https` и `*.purs.gov.rs`);
   на транзиентный сбой — один быстрый повтор.
2. Вырезает из HTML видимый текст (без `<script>`/`<style>`) — это «сырой текст чека».
3. Отправляет его в Gemini 2.5 Flash вместе со списком категорий пользователя и схемой ответа.
4. Модель возвращает строгий JSON — позиции (с уже очищенными названиями), категорию каждой
   позиции строго из списка пользователя, дату и итог чека.
5. Функция приводит числа к `number` и оставляет только категории из списка пользователя,
   сопоставляя названия нормализованно (регистр/пробелы/NFKC) и отдавая написание пользователя;
   Mini App затем привязывает категорию к своей категории нечётко (синонимы, вхождение, ID).

## Почему категории раньше определялись «со 2-3 раза» и что сделано

Mini App передаёт в запросе `categories` из своего дашборда. Если скан уходил раньше, чем
Firestore отдавал дашборд, список категорий был пустым → функция подставляла свой список,
и названия категорий не совпадали с категориями пользователя (позиции приезжали без
категорий). Дополнительно первый «холодный» запрос к сайту чека/Gemini иногда падал —
пользователь сканировал заново, и со второго раза всё работало.

Что делает клиент (`apps/mini-app/src/main.tsx`):

- ждёт категории пользователя через ref на дашборд (без «устаревшего» state);
- **никогда не отправляет пустой список**: если дашборд не пришёл за 5 с, уходит стартовый
  список текущего языка — ровно те же названия, что лежат в Firestore у нового пользователя
  (`defaultDashboard`), плюс `lang` в теле запроса;
- отменяет предыдущий незавершённый запрос через `AbortController` (ответ гонки не перезаписывает свежие данные);
- дебаунсит повторные срабатывания QR-сканера (300 мс) и блокирует повторные запуски, пока идёт распознавание;
- обновляет позиции и их категории одним `setState` (атомарно);
- сопоставляет категорию от модели с категорией пользователя нормализованно (регистр, пробелы, NFKC).

Что делает функция (`api/parse-receipt.js`):

- держит fallback-список **синхронным с клиентом** (`DEFAULT_CATEGORIES_BY_LANG`: ru/en/sr) и выбирает его по `lang`;
- повторяет сбои по разным правилам, уважая лимит Gemini Free Tier (5 RPM):
  - **429 (лимит запросов)** — повтор **той же** модели с растущей паузой 2 с → 4 с
    (`RATE_LIMIT_RETRIES = 2`): квота считается на ключ, переключение модели не помогает;
  - **503 «high demand» / таймаут / 5xx / 404 (модель снята)** — следующая модель цепочки
    `gemini-3.8 → 3.7 → 3.6`;
  - **400/401/403** — сразу наружу, повтор бессмыслен;
  - скачивание страницы чека повторяется один раз (таймаут 10 с на попытку); весь бюджет
    укладывается в `maxDuration: 60` функции на Vercel;
- сравнивает категории от модели с категориями пользователя нормализованно
  (регистр/пробелы/NFKC), а в ответе отдаёт написание пользователя.

Защита от лимита на клиенте (`apps/mini-app/src/main.tsx`): дебаунс 600 мс (дубли `qrTextReceived`
схлопываются в один вызов), запрет нового запроса, пока предыдущий в работе
(`parseInFlightRef`), и очистка таймера/запроса при размонтировании.

Диагностика: `[AI Parse Sent]` / `[AI Parse Received]` в консоли Mini App и предупреждение
`parse-receipt: клиент не передал categories — беру стартовые категории языка «…»` в логах функции.

## Почему позиции падали в «Остальное» и что сделано

Модель могла вернуть категорию своим названием («Продукты», «Groceries»), которого нет в списке
пользователя («Еда»), — и позиция уходила в «Остальное». Плюс названия товаров приходили с
фискальным мусором сербских чеков («KOM (Ђ)», «KOM (E)»), что мешало и разбору, и чтению списка.

Что сделано:

- **список категорий фиксируется в системной инструкции** (не только в промпте): «Каждая позиция
  ДОЛЖНА быть отнесена к одной из следующих категорий строго из списка: […]. Не придумывай новые
  категории. Если ни одна категория из списка не подходит — null»; тот же список уходит в `enum`
  схемы ответа и дублируется в промпте;
- **правило очистки названий** — в системной инструкции и в описании поля `name` схемы: «убирай
  фискальные суффиксы „KOM (Ђ)“, „KOM (E)“, „KOM“, служебные коды… Пример: „SOK COCA COLA ZERO
  1,5L KOM (Ђ)“ -> „Sok Coca Cola Zero 1.5L“»;
- **форматирование названия по количеству** — там же: «если `qty > 1`, добавь к названию суффикс
  „{Название} {qty} kom“ (например, „Voda 3 kom“); если `qty == 1` — только название („Hleb“,
  без „1 kom“)»: модель отдаёт уже готовую строку, дополнительная склейка на клиенте не нужна;
- **нечёткое сопоставление на клиенте** (`apps/mini-app/src/categoryMatch.ts`): нормализация
  (Unicode/регистр/пробелы) → точное название → ID → вхождение названий → группы синонимов
  (RU/EN/SR: «Продукты» ~ «Еда» ~ «Groceries» ~ «Hrana», «Кафе» ~ «Тусичи», «Транспорт» ~ «Prevoz» …);
- если совпадения нет — позиция уходит в «Остальное» (не теряется, категорию можно выбрать вручную);
- диагностика: `[Receipt Items Parsed]:` — позиции от сервера и таблица привязки
  (`aiCategory` → `matchedName`, `matchedBy: name | id | contains | synonym | none`),
  чтобы сразу видеть, почему категория привязалась или нет.


## Эндпоинт

```
POST https://serverless-tawny-xi-39.vercel.app/api/parse-receipt   ← канонический путь (использует Mini App)
POST https://serverless-tawny-xi-39.vercel.app/api/receipts/parse  ← алиас из vercel.json (тот же handler)
```

Адрес зафиксирован в клиенте константами `RECEIPT_API_BASE` / `RECEIPT_API_PATH`
(`apps/mini-app/src/main.tsx`): `VITE_API_URL` переопределяет только базу (в dev пустое значение
уходит на vite-прокси `/api` → `localhost:3001`), а в продакшене без переменной используется
именно этот деплой — приложение больше не падает с «API не настроен».

Запрос:

```json
{ "qrUrl": "https://suf.purs.gov.rs/v/?vl=...", "categories": ["Еда", "Транспорт"], "lang": "ru" }
```

Вместо `qrUrl` можно передать уже готовый сырой текст чека — тогда страница не скачивается:

```json
{ "text": "VODA MINERALNA 0,5L KNJA KOM (Ђ)\n1,00 57,99 57,99\nУкупан износ 57,99", "categories": ["Еда"] }
```

> Mini App передаёт именно `qrUrl`: у клиента есть только содержимое QR, а страницу `suf.purs.gov.rs`
> скачивает и разбирает сама функция. Вариант с `text` — для ручной вставки текста и других клиентов.

`categories` опциональны: Mini App всегда передаёт свои (или стартовый список языка), а функция
использует их как fallback по `lang`, если список всё-таки пустой:

| `lang` | Fallback-список (совпадает с новым пользователем в Mini App) |
| --- | --- |
| `ru` (по умолчанию) | `["Еда", "Транспорт", "Покупки"]` |
| `en` | `["Food", "Transport", "Shopping"]` |
| `sr` | `["Hrana", "Prevoz", "Kupovina"]` |

Именно этот список уходит в схему ответа модели (`enum`), поэтому Gemini всегда выбирает
категорию только из категорий пользователя (или `null`, если ничего не подошло).

Ответ `200` — ровно тот JSON, который по схеме возвращает модель:

```json
{
  "dateTime": "2026-09-16T17:50:44",
  "items": [{ "name": "VODA MINERALNA 0,5L", "qty": 1, "price": 57.99, "total": 57.99, "category": "Продукты" }],
  "total": 377.96
}
```

`dateTime` — **локальное время чека в ISO 8601 без часового пояса** (`YYYY-MM-DDTHH:mm:ss`).
Сервер принудительно срезает `Z` и `±HH:MM`, если модель их дописала: иначе клиент счёл бы
17:50 временем UTC и прибавил локальный пояс (в UTC+2 на экране стало бы 19:50). Нераспознанная
дата (например `31.02`) превращается в `null`, а не в «какую-то» дату.

Ошибки: `{ "error": "..." }`

| Статус | Когда |
| --- | --- |
| `400` | нет `qrUrl` / `text`, либо некорректный или чужой URL (не `*.purs.gov.rs`) |
| `405` | метод не `POST` |
| `422` | страница получена, но текст пуст или модель не нашла ни одной позиции |
| `429` | исчерпан лимит Gemini (5 RPM) даже после повторов; в теле ещё `code: "RATE_LIMITED"`, клиент показывает локализованный текст |
| `502` | сайт чека недоступен / вернул ошибку, либо Gemini вернул ошибку |
| `503` | не задан `GEMINI_API_KEY`, снятая модель/невалидный ключ, либо Gemini перегружен (503 «high demand») |
| `500` | внутренняя ошибка |

Без AI разбора больше нет: если ключ не задан или Gemini недоступен, функция честно
возвращает ошибку, а не «пустой чек» — позиции с `category: null` приходят только тогда,
когда модель реально не подобрала категорию.

## Деплой

```bash
cd apps/serverless
npx vercel login
npx vercel --prod          # выдаст https://<project>.vercel.app
npx vercel env add GEMINI_API_KEY production   # вставить ключ из https://aistudio.google.com/apikey
npx vercel --prod          # передеплой, чтобы переменная подхватилась
```

Затем в `apps/mini-app/.env`:

```
VITE_API_URL=https://<project>.vercel.app
```

и пересборка мини-аппа (`pnpm --filter @sp3ndly/mini-app build`), после чего `dist` публикуется
на GitHub Pages. Всё — без ngrok и без запущенного локального сервера.

## Чек-лист релиза (важно!)

GitHub Actions собирает и публикует **только Mini App** (`.github/workflows/deploy.yml`).
Serverless-функция на Vercel живёт отдельно и обновляется **только вручную**:

```bash
# 1) фронт (GitHub Pages) — автоматически на push в main
git push origin main

# 2) функция распознавания — отдельный деплой, иначе промпт и логика останутся старыми
cd apps/serverless
npx vercel --prod
# проверить, что ключ задан для production:
npx vercel env ls production | grep GEMINI_API_KEY
```

Если после правок промпта названия товаров всё ещё приходят с «KOM (Ђ)» — функция не
передеплоена: очистку названий делает модель, то есть промпт живёт в функции, а не в бандле фронта.

### Telegram кэширует Mini App

GitHub Pages отдаёт `index.html` с `cache-control: max-age=600`, а Telegram WebView держит
свою копию страницы. Чтобы гарантированно получить свежую сборку:

1. полностью закрыть Mini App (смахнуть приложение/вкладку) и открыть заново;
2. если не помогло — BotFather: `/myapps` → выбрать бота → Bot Settings → Configure Mini App →
   сохранить URL (это сбрасывает кэш Telegram);
3. крайний случай — добавить cache-buster к URL: `.../spendly/?v=2` и сохранить в BotFather.

Проверить, какая сборка реально загружена, можно по имени бандла:

```bash
curl -s https://n0rg3.github.io/spendly/ | grep -o 'assets/[^"]*'   # должно совпасть с
cat apps/mini-app/dist/index.html | grep -o 'assets/[^"]*'          # локальной сборкой
```

### Переменные окружения

| Переменная | Обязательна | Описание |
| --- | --- | --- |
| `GEMINI_API_KEY` | да | Ключ Gemini (https://aistudio.google.com/apikey). Без него распознавание чеков недоступно (503). |
| `GEMINI_MODEL` | нет | По умолчанию `gemini-3.8-flash` — модель с поддержкой Structured Outputs (`responseSchema`). Старые ID (например `gemini-2.5-flash`) Google выводит из продажи: вызов снятой модели отдаёт 404 и функция отвечает 502. |

| `RECEIPT_RETRY_DELAY_MS` | нет | Пауза между повторными попытками при транзиентном сбое (по умолчанию 500 мс; `0` — без паузы, используется в тестах). |

## CORS

По умолчанию разрешены `https://n0rg3.github.io`, `http://localhost:5173`, `http://127.0.0.1:5173`.
Запросы без `Origin` (curl, Telegram-клиент) проходят. Источники из белого списка получают
`Access-Control-Allow-Origin` со своим значением; чужим доменам заголовок не отдаётся — браузер
блокирует запрос.

## Безопасность

- URL чека валидируется: только `https:` и только домены `*.purs.gov.rs` (защита от SSRF).
- Таймаут запроса к сайту чека — 12 секунд на попытку (плюс один повтор), запроса к Gemini — 15 секунд.
- Ключ Gemini живёт только в env Vercel — в клиентский бандл не попадает.

## Примечание про парсинг

Страница чека отдаётся без отрендеренной таблицы (её рисует Knockout.js на клиенте), поэтому
функция берёт текстовый дамп чека из `<pre>` панели `#collapse3` (fallback — `#PrintInvoice`
и `body`) и передаёт его модели. Название товара может быть на отдельной строке от чисел
`<цена> <кол-во> <итог>` — такие случаи разбирает LLM, а не серверные регулярки. Логика 1:1
повторяет `apps/api/src/index.ts`.

## Формат ответа модели (responseSchema)

Модель всегда возвращает объект строго такого вида (JSON Mode, `temperature: 0`):

```json
{
  "dateTime": "2026-09-16T17:50:44",
  "items": [
    { "name": "Sok Coca Cola Zero 1.5L", "qty": 1, "price": 134.99, "total": 134.99, "category": "Еда" }
  ],
  "total": 194.98
}
```

- `items` — все позиции чека: `name`, `qty`, `price` (за единицу), `total` (по позиции), `category`.
- `name` — готовое к показу название от модели: без фискальных пометок («KOM (Ђ)», «KOM (E)») и
  служебных кодов, и уже с суффиксом количества при `qty > 1` («Voda 3 kom»); при `qty == 1` — только
  название («Hleb», без «1 kom»). Склейка на клиенте не требуется.
- `category` — только значение из списка пользователя (`enum` в схеме) либо `null`; на клиенте оно
  дополнительно сопоставляется с категориями пользователя нечётко (см. раздел про «Остальное»).
- `dateTime` — время покупки ровно как напечатано на чеке, `YYYY-MM-DDTHH:mm:ss` **без `Z` и без
  смещения** (в схеме намеренно не указан `format: "date-time"`: он требует RFC 3339 и модель
  дописывает «Z», что сдвигает время на +2 часа); `total` — итог чека.
